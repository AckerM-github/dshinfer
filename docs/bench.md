# 压测报告：dshinfer vs llama-server 原生

> 2026-11-08 · RTX 4060 Laptop 8 GB · DeepSeek-V4-Pro-Qwen3.5-9B Q4_K_M (5.24 GB) · 8192 ctx × 4 slots

## 1. 这份报告想回答什么

推理服务层写完，最该回答的问题不是「快不快」，而是：

1. **我们自己写的那一层，到底吃掉了多少性能？**
2. 吞吐的天花板在哪，是被服务层挡住了，还是被硬件挡住了？
3. 哪些默认配置会在不声不响地把容量砍半？

为了把「服务层开销」单独分离出来，对照端点选了 **llama-server 的原生接口**，
而不是 vLLM——因为 vLLM 需要 Linux + 较新的 CUDA，本机是 Windows + 8 GB 显存，
9B 模型连权重都放不进去。用同一个引擎的原生接口做对照，变量只剩「我们这一层」。

## 2. 方法

| 项 | 设置 |
|---|---|
| 端点 A | `POST :8000/v1/chat/completions`（我们的服务：模板渲染 + 调度 + SSE 重编码） |
| 端点 B | `POST :8124/completion`（llama-server 原生，prompt 由脚本用同一份模板渲染） |
| 并发档位 | 1 / 2 / 4 / 8 |
| 每档请求数 | 12 |
| 生成长度 | `max_tokens=64`，`temperature=0` |
| 指标 | 墙钟、req/s、tok/s、TTFT（首内容块）、E2E |

每档先预热一次，避免首个请求的 kernel 编译和缓存冷启动污染数据。
脚本：`scripts/bench_load.py`。

## 3. 结果（最终配置：租户配额关闭）

| 并发 | 端点 | 成功 | 墙钟(s) | req/s | tok/s | TTFT p50 | TTFT p95 | E2E p50 | E2E p95 |
|---|---|---|---|---|---|---|---|---|---|
| 1 | dshinfer | 12/12 | 19.20 | 0.63 | 40.0 | 101 ms | 140 ms | 1597 ms | 1629 ms |
| 1 | 原生 | 12/12 | 19.01 | 0.63 | 40.4 | 80 ms | 83 ms | 1571 ms | 1581 ms |
| 2 | dshinfer | 12/12 | 10.65 | 1.13 | 72.1 | 148 ms | 159 ms | 1773 ms | 1785 ms |
| 2 | 原生 | 12/12 | 10.57 | 1.14 | 72.7 | 114 ms | 149 ms | 1761 ms | 1764 ms |
| 4 | dshinfer | 12/12 | 6.28 | 1.91 | 122.4 | 193 ms | 240 ms | 2077 ms | 2115 ms |
| 4 | 原生 | 12/12 | 6.14 | 1.96 | 125.2 | 183 ms | 238 ms | 2038 ms | 2065 ms |
| 8 | dshinfer | 12/12 | 6.17 | 1.94 | 124.4 | 2194 ms | 2305 ms | 4062 ms | 4146 ms |
| 8 | 原生 | 12/12 | 6.14 | 1.95 | 125.1 | 2163 ms | 2257 ms | 4023 ms | 4161 ms |

服务层相对原生的开销：

| 并发 | 吞吐损失 | TTFT 增加 |
|---|---|---|
| 1 | +1.0% | +21 ms |
| 2 | +0.8% | +34 ms |
| 4 | +2.2% | +11 ms |
| 8 | +0.6% | +31 ms |

**结论：服务层成本 ≈ 1–2% 吞吐 + 20–35 ms 首字延迟。** 那 20 多毫秒来自多一跳 HTTP、
一次 SSE 解析与重编码，以及模板渲染（有 `lru_cache`，稳定在 1 ms 内）。对交互式场景这是可接受的价格；
对延迟极其敏感的批处理，这一跳就是纯开销。

## 4. 反例：一个默认值可以静默砍掉 42% 吞吐

第一版把 `per_tenant_inflight` 默认设成 2（想当然的「公平」），结果：

| 并发 | 端点 | tok/s | TTFT p50 | TTFT p95 |
|---|---|---|---|---|
| 4 | dshinfer（配额=2） | 72.7（−41.7%） | 1860 ms | 1909 ms |
| 4 | 原生 | 124.8 | 204 ms | 224 ms |
| 8 | dshinfer（配额=2） | 72.8（−43.7%） | 4512 ms | 5425 ms |
| 8 | 原生 | 129.4 | 2115 ms | 2141 ms |

原因很简单：单租户配额 2 < `max_concurrency` 4，于是**所有单客户端请求最多只有 2 个在飞**，
4 个槽位里永远空着 2 个。吞吐卡在「并发 2」的水平，延迟却按「并发 4/8」的排队算。

这也是压测的价值：如果不是跑了一遍，这个默认值会一直躺在那儿，线上表现为
「机器明明闲着，用户却在等」。现在默认 0（不限制），多租户部署时才显式设成
`max_concurrency // 租户数`，并且必须重新压一遍尾延迟。

## 5. 天花板在哪

- **单流 40 tok/s**：这是 9B Q4 模型在 8 GB 笔记本卡上的正常水平（显存带宽 ~256 GB/s，
  权重 0.92 GB… 但这是量化后的 5.24 GB，读一遍就是 20 ms 量级）。
- **4 槽位饱和 ≈ 125 tok/s**：并发从 4 到 8 吞吐几乎不再涨（124.4 → 124.4），
  说明 4 个槽位已经打满；8 并发时多出来的请求在引擎侧排队，TTFT 从 193 ms 跳到 2194 ms。
- **带宽墙估算 ≈ 278 tok/s**：按权重 0.92 GB 有效读取 + 256 GB/s 粗算的上限，当前到位约 45%。
  剩下的差额是 attention/KV 读写和 kernel 启动，不是服务层的锅。

**结论：瓶颈在引擎与显存带宽，不在服务层。** 服务层的价值不在 throughput，而在
「把有限的吞吐分配给对的请求」——优先级实验里对话等待从 7.37 s 降到 3.44 s，就是这个价值。

## 6. 与 vLLM 的定性对照（没跑，说明为什么）

| | dshinfer + llama.cpp | vLLM |
|---|---|---|
| 平台 | Windows，单卡 8 GB | Linux，需要较新 CUDA |
| 本机能否跑 9B | 能（Q4_K_M 5.24 GB） | 不能（bf16 18.8 GB，且 Windows 无官方支持） |
| 批处理粒度 | 引擎内部 4 个 slot | token 级 continuous batching + PagedAttention |
| 前缀缓存 | slot 内 KV，batch 边界对齐（实测只命中 117/629） | 块级哈希前缀缓存，跨请求共享 |
| 调度 | 我们的服务层（优先级/老化/配额/亲和） | 引擎内的 scheduler（chunked prefill、抢占） |

真正该学的不是「vLLM 快」，而是它把 **KV 当页管理、把请求当流调度** 这两件事做到了引擎内部。
我们的服务层只能在请求粒度上做取舍——这也是为什么「连续批处理」这一项我们诚实地留在了路线图的
「引擎能力」里，而不是假装在服务层实现。

## 7. 复现

```powershell
$env:DSHINFER_ENGINE="llamacpp"
uv run uvicorn dshinfer.api:app --port 8000     # 会自动拉起 llama-server
uv run python scripts/bench_load.py             # 四档并发 × 两个端点
uv run python scripts/bench_sched.py            # 优先级 / 前缀缓存实验
```
