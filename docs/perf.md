# 性能报告：把 9B 模型压到 RTX 4060 Laptop 的极限

> 目标不是"能跑"，而是**知道天花板在哪、离它多远、剩下的空间该往哪花**。
> 全部数字都是本机实测，命令在每节末尾，可逐条复现。

## 0. 结论（先看这五条）

| # | 结论 | 证据 |
|---|---|---|
| 1 | **生成阶段已经在带宽墙的 90%**，调任何启动参数都推不动 | 43.4 tok/s vs 理论上限 48.4 |
| 2 | 预填充是唯一还能靠参数改善的环节，`-ub 1024` 换来 +10% | 2170 → 2400 tok/s |
| 3 | **批处理是最大的剩余杠杆**：4 条并发聚合 143.7 tok/s（3.4 倍） | 单流 42.6 → 4 流 143.7 |
| 4 | **前缀缓存命中 99%**，多轮对话预填充从 633 ms 降到 115 ms | 906 token × 4 轮 |
| 5 | 投机解码在本模型对上是**负收益**（接受率 16–31%），量化降档也不划算（+18% 速度赔 +58% 困惑度） | ×0.47 与 PPL 7.74→12.20 |

一句话：**单条对话的延迟已经没有免费的午餐；想要更多吞吐只能靠并发，想要更低延迟只能换更小的模型或更快的卡。**

## 1. 硬件与理论天花板

| 项 | 值 |
|---|---|
| GPU | RTX 4060 Laptop，8 GB，24 SM，sm_89 |
| 显存带宽 | ≈272 GB/s（128-bit @ 17 Gbps 的有效值） |
| 权重（Q4_K_M） | 5,629,111,264 B = 5.63 GB |
| 每次生成 1 token 必读 | 全部权重（batch=1 时） |
| 理论上限 | 272 ÷ 5.63 = **48.4 tok/s** |
| 实测（tg128） | **43.4 tok/s = 上限的 90%** |

生成阶段每个 token 都要把 5.6 GB 权重从显存读一遍，算力完全不是瓶颈（实测利用率个位数）。
所以"生成 43 tok/s"不是没调好，是**物理上限**。

```powershell
cd D:\llm\runtime\llama.cpp
.\llama-bench.exe -m <gguf> -ngl 99 -p 512 -n 128 -r 3
```

## 2. 启动参数扫描：只有预填充能动

`-p 512 -n 128 -r 3`，CUDA，build 12202：

| 配置 | pp512 (tok/s) | tg128 (tok/s) | 相对基线 |
|---|---|---|---|
| 基线 | 2170.60 ± 89.77 | 43.13 ± 0.12 | — |
| `-fa 1` | 2381.30 ± 58.86 | 43.43 ± 0.03 | 预填充 +9.7% |
| `-ctk q8_0 -ctv q8_0` | 2387.76 ± 20.18 | 43.30 ± 0.05 | KV 减半，速度不变 |
| **`-ub 1024`** | **2399.34 ± 33.08** | 43.45 ± 0.09 | **预填充 +10.5%** |
| `-b 2048 -ub 1024` | 2397.22 ± 13.94 | 43.39 ± 0.20 | 与上者等价 |
| `-t 8` | 2394.75 ± 9.68 | 43.41 ± 0.11 | 无差别（GPU 满载） |

**读法**：生成那列在所有配置下都是 43.x —— 一个带宽受限的系统，参数怎么调都不会动。
真正有收益的是把预填充的微批拉到 1024。这个值已经写进 `.env`（`N_UBATCH=1024`）。

## 3. 上下文越深，生成越慢（KV 读取代价）

`-p 0 -n 128 -d <depth>`：

| 已填充上下文 | tg128 (tok/s) | 相对 d0 |
|---|---|---|
| 0 | 42.96 ± 0.17 | — |
| 4,096 | 42.05 ± 0.10 | −2.1% |
| 16,384 | 39.32 ± 0.09 | −8.5% |

原因：每步除了读权重，还要读整段 KV cache。16K 上下文时 KV 是 0.5 GB 量级，
相当于给 5.6 GB 的权重又加了 10% 的读取量。

**推论**：DSH 这种长上下文场景，速度会随对话变长缓慢下降，这是预期行为，不是 bug。

## 4. 预填充：约 2300 tok/s，长 prompt 的冷启动账

| prompt 长度 | pp (tok/s) | 耗时 |
|---|---|---|
| 512 | 1,997.90 ± 68.31 | 0.26 s |
| 2,048 | 2,362.45 ± 29.05 | 0.87 s |
| 8,192 | 2,322.09 ± 8.50 | 3.53 s |

2K 以上就稳定在 ~2300 tok/s（注意力在 8K 还没成为瓶颈）。
**这决定了 DSH 冷启动的首字延迟**：系统提示 + 工具定义约 3–6K token → **1.3–2.6 秒**。
下一节的缓存命中直接把这段抹掉。

## 5. 前缀缓存：多轮对话的真正加速器

同一个 906 token 的 prompt，四轮请求（`cache_prompt: true`，单 slot）：

| 轮次 | 请求 | prompt_n | cache_n | 复用率 | 预填充耗时 |
|---|---|---|---|---|---|
| 1 | 冷启动 | 906 | 0 | 0% | **633 ms** |
| 2 | 一字不差 | 4 | 902 | 99.6% | 424 ms |
| 3 | 末尾追加一问 | 7 | 906 | 99.2% | **115 ms** |
| 4 | 再追加 | 5 | 913 | 99.5% | 121 ms |

**读法**：llama.cpp 按最长公共前缀复用 KV，只重算新增部分。
多轮对话里，第 2 轮之后预填充成本几乎归零（633 → 115 ms，5.5 倍）。

**但有个前提**：**同一条序列的延续**。第 2 轮之所以 99% 命中，是因为新 prompt
把上一轮 prompt 整段当作前缀。换成"同一段 system + 四个不同问题"，命中率立刻归零
（见 5.2）。这也是当前默认 `N_PARALLEL=4` 的原因：既然并发下缓存本来就不共享，
不如拿并发换吞吐（单流 42 → 4 路聚合 110 tok/s）。

### 5.1 端到端验证（流式 + 服务层 + 工具解析都在路上）

`scripts/probe_perf_service.py`，同一个 900 token 系统提示 + 三轮追问：

| 轮次 | prompt | cached | TTFT | 输出 | 端到端速度 |
|---|---|---|---|---|---|
| 1 | 901 | 0 | **951 ms** | 96 tok / 3.57 s | 26.9 tok/s |
| 2 | 935 | 897（96%） | **189 ms** | 96 tok / 2.79 s | 34.5 tok/s |
| 3 | 963 | 931（97%） | 196 ms | 96 tok / 2.80 s | 34.2 tok/s |

服务层的解码速度 ≈ **36–37 tok/s**（扣掉首字延迟后），比裸引擎的 42.9 低约 14%，
差额是 SSE 逐帧编码 + Python 侧逐 token 回调；换来的是取消、超时、工具解析、
指标这些能力。首字延迟被前缀缓存从 951 ms 压到 190 ms，这才是多轮对话的体感来源。

> 顺带修掉一个隐蔽 bug：模板渲染时如果传 `dict` 给 jinja，带 assistant 历史会让
> `message.tool_calls is iterable` 抛 UndefinedError → 整段渲染失败 → 退回没有
> `<think></think>` 护栏的裸 ChatML → 模型自己开思考块，96 个 token 全耗在
> 思考上、正文一个字没有。改成传 pydantic 对象后恢复，`tests/test_render.py`
> 加了回归用例。

### 5.2 跨请求前缀共享：这个模型上做不到，而且是架构决定的

第一反应是"共享 system 前缀应该能命中"，于是把能想到的开关全试了一遍
（`scripts/bench_cache_reuse.py`，独立引擎、独占显存、同一段 ~300 token 前缀、
四个不同问题）：

| 配置 | 串行 4 条 cache_n | 并发 4 条 cache_n |
|---|---|---|
| 默认（`cache-reuse` 关闭） | `[0, 0, 0, 0]` | `[0, 0, 0, 0]` |
| `--cache-reuse 256` | `[0, 0, 0, 0]` | `[0, 0, 0, 0]` |
| `--cache-reuse 256` + 全部 `id_slot=0` | `[0, 0, 0, 0]` | — |
| 服务层 `SLOT_PINNING=true` | `[0, 0, 0, 0]` | `[0, 0, 0, 0]` |

同时刻的预填充耗时都是 212–298 ms，也就是**每次都完整重算**。

根因不在开关，在架构：这个模型 33 层里只有 **7 层是全注意力**，另外 **26 层是
线性注意力（recurrent）**。循环层维护的是一份"跑到当前位置的摘要状态"，不是
每个 token 的 K/V —— 没有可以按块切分、按页表拼装的 KV 可以复用。所以：

- 同一序列往前推进（多轮对话）→ 状态自然延续，99% 命中；
- 换一个问题共用 system 前缀 → 状态必须从第一个 token 重跑，命中率 0。

`--cache-reuse` 做的是 KV shifting（把已有 KV 平移对齐），对 recurrent 层无效；
`id_slot` 钉死只影响调度，不改变"循环层无法分支"这件事。

**工程结论**：在这类混合架构上，前缀缓存能省的只有"同一条对话的延续"，不要指望
多用户共享 system prompt 能省钱。要在服务层省这部分，只有一条路——把共享前缀
做成**独立的一次预填充**再复用状态，而 llama.cpp 没有暴露这个能力（DeepSeek 自己
的 MLA + 线性注意力栈才有）。这条记为"已知不可得"，不再尝试。

## 6. 批处理：唯一能大幅提高吞吐的杠杆

`llama-batched-bench -npp 512 -ntg 128 -npl 1,2,4`：

| 并发序列 | 每流生成 (tok/s) | **聚合生成 (tok/s)** | 聚合总吞吐 (tok/s) | 预填充 (tok/s) |
|---|---|---|---|---|
| 1 | 42.59 | 42.59 | 193.92 | 1,735 |
| 2 | 39.93 | **79.85**（×1.87） | 345.60 | 2,057 |
| 4 | 35.92 | **143.69**（×3.37） | 575.00 | 2,304 |

**读法**：权重只读一次却能服务 4 条序列 → 聚合吞吐接近 4 倍；
代价是每条流自己慢了 16%（42.6 → 35.9）。
这是带宽受限系统里最经典的取舍：**吞吐换延迟**。

**对我们意味着**：单用户聊天用 1 个 slot；跑批量评测 / 多 agent 并行时把
`N_PARALLEL` 调到 4，聚合吞吐从 43 涨到 143 tok/s（但每条上下文从 32K 摊到 8K）。

## 6.5 服务层开销：3%，不是 30%

同一脚本 `scripts/profile_stream.py`、同一 600 token 前缀、`n_predict=128`、并发 4：

| 端点 | 单流 (tok/s) | 4 并发聚合 (tok/s) | TTFT 中位 | 前缀缓存命中 |
|---|---|---|---|---|
| 直连引擎 `:8124` | 33.6 | **84.2** | 598 ms | 2/4 |
| 服务层 `:8000`（不钉 slot，现默认） | 33.2 | **81.4** | 998 ms | 0/4 |
| 服务层 `:8000`（`SLOT_PINNING=true`） | — | 79.0 | 988 ms | 0/4 |

三条结论：

1. **服务层吞吐开销 3.3%**（84.2 → 81.4）。之前记的"服务 66–75 vs 引擎 111"是**两次不可比的测量**：前者带 600 token 前缀，后者是短 prompt 短输出，而解码速率随上下文变深本来就会掉（见 §3）。教训：对照实验必须同工况，否则会把"换了 workload"误判成"换了实现"。
2. **`id_slot` 钉死只再掉 3%**，真正的问题是它让前缀缓存几乎不可能命中（0/4）—— 槽位被钉死，引擎没法把请求拼到已缓存该前缀的槽上。
3. **真正落后的是 TTFT（+400 ms）**：4 路请求的前缀全部没命中，各自重算 600 token。这是 §5 前缀缓存在并发下的真实边界，也是下一步（跨 slot 前缀共享）要解决的问题。

## 7. 投机解码：在这个模型对上不成立

草稿模型 `Qwen3.5-0.8B-Q8_0`（812 MB），目标 9B Q4_K_M：

| 配置 | 生成 (tok/s) | 相对基线 | 接受率 | 显存 |
|---|---|---|---|---|
| 基线 | 41.91 | 1.00 | — | 5,491 MiB |
| draft-4 | 21.64 | 0.52 | 35/112 = 31% | 6,485 MiB |
| draft-8 | 19.05 | 0.45 | 34/216 = **15.7%** | 6,485 MiB |
| draft-12 | 18.11 | 0.43 | — | 6,485 MiB |
| ngram-simple | 41.81 | 1.00 | — | 5,491 MiB |

投机解码的收益 = 接受率决定的：接受率高时一次前向出多个 token，接受率低时
每个被拒的草稿都是纯浪费，还要多读一遍 812 MB 的草稿模型。

**为什么接受率低**：草稿是官方 Qwen3.5-0.8B，目标是**被蒸馏 + heretic 微调过**的 9B，
分布已经偏了。反过来，在高度可预测的文本上（单条公式化短 prompt）实测
**68.5 tok/s、56/56 全接受** —— 说明机制没错，是模型对不匹配。

## 8. 量化降档：速度买得到，质量赔更多

语料 `D:\llm\data\corpus.txt`（4.45 MB 中文小说），`llama-perplexity -c 512 --chunks 40`：

| 量化 | 大小 | pp512 | tg128 | **困惑度 PPL** |
|---|---|---|---|---|
| Q4_K_M（当前） | 5.23 GiB | 2,399 | 43.45 | **7.74 ± 0.18** |
| Q3_K_M | 4.30 GiB | 2,277 | **51.08** | **12.20 ± 0.32** |

## 9. 配置档位（按场景选，不要一档通吃）

一次干净的 A/B（同一 prompt、同一二进制，只改 `-np` 与 `--kv-unified`）：

| 配置 | 单流 | 4 并发 | 说明 |
|---|---|---|---|
| `-np 1`（旧默认） | 31.9 | 85.3（串行，各流 10–41 不均） | 长上下文优先，没有并行 |
| `-np 1 --kv-unified` | 37.2 | 85.1 | 统一池对单槽没有额外收益 |
| **`-np 4 --kv-unified`（新默认）** | **37.6** | **111.1（各流 27.6–28.1，均匀）** | 两者兼得 |

所以 `.env` 现在默认 `N_PARALLEL=4` + `KV_UNIFIED=true`：单个长请求仍能吃到整块 32K，
多条短请求并行跑，聚合吞吐 42 → 111 tok/s。

按场景微调：

| 场景 | `N_CTX` | `N_PARALLEL` | `KV_UNIFIED` | 预期 |
|---|---|---|---|---|
| **单 agent 长对话（DSH 默认）** | 32768 | 4 | true | 单流 37.6，缓存命中后首字 ~200 ms |
| 纯串行、要绝对最低延迟 | 32768 | 1 | false | 单流 31.9，但并发时串行排队 |
| 批量评测 / 多 agent | 8192 | 4 | true | 每流 ~28，聚合 **~111** |
| 极低显存 | 32768 | 1 | true、`-ctk q8_0 -ctv q8_0` | KV 减半，换更长上下文 |

改完重启服务生效（`.env` 里改，或 `DSHINFER_N_PARALLEL=4` 环境变量）。

## 10. 还没做的，以及为什么

| 方向 | 为什么没做 |
|---|---|
| Continuous batching（token 级） | 在 llama.cpp 内部，我们这层碰不到；要自己实现就得接管 KV 和 token 循环 —— 那等于重写引擎 |
| PagedAttention | 引擎内部的事。但它的**第一条收益**（不按最大长度预留、按需分配）llama.cpp 已有等价物：`--kv-unified`。实测 `-np 4` 不统一时 4 槽各切 8K、且单请求吃不到 32K；统一后 4 槽共享一个 32K 池，单流 37.6 / 4 并发 111 tok/s。**缺的是第二条**：跨序列的前缀块共享（vLLM 的 radix cache）—— 实测同一 system prompt 四路并发，只有 1/4 的请求命中缓存，其余各重算一遍 |
| MTP / EAGLE3 投机 | 该 GGUF 转换时没带 MTP 头；EAGLE3 需要专门的草稿头 |
| 换 30B-A3B（MoE） | 8 GB 显存放不下（激活 3B 但权重 18 GB+） |
| 更高带宽的卡 | 5070 Ti（896 GB/s）理论 159 tok/s，是唯一能突破 48 的硬件路径 |

## 12. 上下文档位：为什么从 32K 提到 64K

**动机**：接 DSH 之后，实测 prompt 24,359–27,957 token（系统提示 + 工具定义 + 历史），32K 只剩 4–8K 余量。开思考必被截断，长文件也读不进去。

**三条路**（同一张卡，8 GB）：

| 方案 | 显存（加载后） | 上下文 | 代价 |
|---|---:|---:|---|
| 32K + f16 KV（旧默认） | 6,161 MiB | 32K | — |
| 64K + f16 KV | 超出 8 GB | — | 不可行 |
| **64K + q8_0 KV（新默认）** | **6,727 MiB** | **64K** | PPL +0.09% |

**质量代价**（同语料、同参数，40×512 token）：

| KV 类型 | PPL | pp512 | tg128 |
|---|---:|---:|---:|
| f16（基线） | 7.7389 ± 0.18441 | 2399.34 | 43.45 |
| q8_0 | **7.7457 ± 0.18471** | 2390.32 | 43.13 |

+0.09% 的困惑度，换上下文翻倍 —— 在这台机器上没有更便宜的选项。

**实测可用深度**（服务层，`max_tokens=32`，思考关闭）：

| prompt token | 耗时 | 预填充速度 | 备注 |
|---:|---:|---:|---|
| 17,892 | 11.5 s | 1,556 tok/s | 冷启动 |
| 35,764 | 13.6 s | 2,638 tok/s | `cached=16,864`（前缀复用） |

32K 时代这两条都会失败；现在 35K 的 prompt 只花 13.6 秒。

**注意**：33 层里 26 层是线性注意力，那部分的循环状态**不参与** KV 量化（llama.cpp 只量化全注意力层的 KV）。所以 q8 的收益全部来自那 7 层，也说明这个模型的"长上下文成本"本来就比别人低。
