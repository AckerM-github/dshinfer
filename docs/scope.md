# 边界清单：哪些是我们写的，哪些不是

> 混乱通常来自分不清「这行代码是我该写的」和「这是别人写好的」。
> 这份清单按层切开，每一层只回答一个问题：**这一层的责任归谁。**

## 一句话定位

我们是**第 3 层（服务层）的实现者**，同时是**第 2 层（推理引擎）的使用者**。
模型权重、KV 管理、算子、批处理调度都在 llama.cpp 里，我们碰不到也不该碰。

```
5 应用   DSH GUI                    ← 别人写的
4 编排   agent 循环 / 工具 / 评测    ← 我们写（部分完成）
3 服务   dshinfer 1,804 行          ← 我们写（已完成）
2 引擎   llama.cpp (C++)            ← 借用
1 权重   GGUF Q4_K_M                ← 下载来的
```

## 一、已经自己实现（1,804 行，17 个文件）

| 模块 | 文件 | 行数 | 职责 |
|---|---|---|---|
| 协议 | `api.py` | 183 | 8 个路由：chat/completions、models、admin、metrics、healthz |
| 服务编排 | `service.py` | 419 | 准入、模板渲染、超时、取消、usage、工具扣尾 |
| 调度 | `scheduler.py` | 189 | 优先级 + 老化 + 租户配额 + 前缀亲和 |
| 引擎适配 | `engine/llamacpp_server.py` | 213 | 拉起 llama-server、SSE 解析、timings 回填、孤儿清理 |
| 引擎生命周期 | `engine/manager.py` | 111 | idle→loading→ready 状态机、热切换 |
| 模型注册 | `registry.py` / `gguf.py` | 237 | 扫 GGUF、解析头部、热发现 |
| 工具调用 | `toolcall.py` | 87 | XML `<tool_call>` → OpenAI `tool_calls` |
| 其余 | config/metrics/logging/schemas/mock | 254 | 配置、指标、日志、请求体、假引擎 |

**共同点**：这些事 llama.cpp **不做**，因为它是引擎不是服务。进程外的东西（协议、并发准入、超时、取消、观测、模型切换）只能我们写。

## 二、借来的（不该自己写）

| 能力 | 提供方 | 为什么不该自己写 |
|---|---|---|
| 权重加载、量化 | llama.cpp + GGUF | 几十种量化格式、CPU/GPU 混合、mmap |
| KV cache 管理 | `--kv-unified` | 统一池 + 按需分配，等于 PagedAttention 收益① |
| 连续批处理调度 | llama.cpp 内部 | token 级调度要接管 KV 和计算图 |
| 算子 / kernel | CUDA kernels | FlashAttention、量化 matmul、融合 |
| 采样（温度/top-p/惩罚） | llama.cpp | 与 KV 状态耦合 |
| 分词 + chat 模板 | GGUF 里的 tokenizer | 模板是训练时固定的，不能自己发明 |

**判断标准**：如果它需要碰「每个 token 的 KV 和计算」，就在引擎里；如果它只关心「请求怎么排队、结果怎么返回」，就在我们这层。

## 四、明确不做的

| 事项 | 理由 |
|---|---|
| 自己实现 PagedAttention / continuous batching | 在 C++ 引擎里；8 GB 单机 4 槽规模也用不上 |
| 自己写注意力/量化 kernel | 这是 llama.cpp 与硬件厂商的领域 |
| 训练 / 微调 | 另一条线，和推理服务无关 |
| 前端 UI | DSH GUI 已经很好；我们要做的是把后端接上去 |
| 多卡并行 | 单卡 8 GB，无意义 |

## 五、怎么判断一个新需求归谁

问三个问题，从上往下：

1. **要碰每个 token 的 KV 或计算图吗？** → 引擎的事，我们只调参数。
2. **只关心请求怎么排队、超时、取消、返回？** → 我们的服务层。
3. **关心"做什么、调用什么工具、结果好不好"？** → 编排层，也要我们写，但独立于服务层。

第 3 类是目前最大的空白：服务层已经能稳定跑，编排层只有 `agent_demo.py` 一个 120 行的演示。
